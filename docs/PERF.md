# 效能：低階手機與 Steam Deck（第 26 輪）

> **先講清楚量測的限制。** 這裡的數字全部來自同一台 Linux 雲端容器裡的 Playwright + Chromium（headless），
> 3D 用 **SwiftShader 軟體繪圖**（CPU 模擬 GPU），不是真的手機或 Steam Deck。量測期間同一台機器上還有其他
> 測試在跑（load average 15–35，只有 4 核），所以**每格畫面時間、FPS 這類數字雜訊很大，只能看相對趨勢，而且這次
> 的前後差距大多落在雜訊內**。可靠的是：下載位元組、draw call / 三角形數、記憶體洩漏測試（客人進出後 geometry
> 與 heap 有沒有回落）。真機（Android 低階機、iPhone、Steam Deck）還沒有實測。

## 量測方式

- 腳本：`tests/e2e/perf.mjs`（預算檢查，已加進 `npm run test:e2e`）；詳細量測腳本另放（每次 before/after 交替跑兩輪取中位數）。
- 兩種裝置設定：
  - **手機**：844×390、deviceScaleFactor 3、觸控、畫質「低」、CDP `Emulation.setCPUThrottlingRate 4`（模擬低階 Android），
    首次載入時另外限速 1.6 Mbps / RTT 150 ms（模擬普通行動網路）。
  - **Deck**：1280×800、DPR 1、畫質「中」、不限速。
- 首次載入：清掉 service worker 與快取後冷啟動；「主選單可操作」= `#m-career` 出現；「第一格營業畫面」= 點地圖後到
  `renderer.info.render.frame > 0`。
- 營業中：3 張地圖（便利商店、超市、加油站），先快轉早上讓客人進店，鏡頭固定在店後方左右掃 10 秒；記錄 rAF 間隔、
  `Game.frame` 主執行緒耗時、`renderer.info`（draw call、三角形）、`performance.memory`、HeapProfiler 取樣的配置量、
  Chrome trace 裡的 GC 事件。為了可比較，量測時關掉 FPS 上限與動態解析度。

### 找到的問題

1. **整個 3D 遊戲（three.js 568 KB + 遊戲程式）都在入口 JS 裡**，主選單要等它全部下載、解析完才出現。
2. **客人離店後模型沒釋放（洩漏）**：每位客人的身體是合併成一個 SkinnedMesh 的獨有 geometry，奧客的配件、手上的籃子、
   拿的東西也都是新合併的 geometry，離店時只從場景移除、沒有 `dispose()`。實測 40 位客人進出後
   renderer geometry 61 → 98、JS heap（GC 後）多了 **11.6 MB**，一整天營業會一直漲（低階手機最後會變慢或被系統殺掉）。
3. 每個新客人第一次出現時，three.js 會對 SkinnedMesh 的每個頂點做骨架變換來算包圍球（每次生客人一個小卡頓）。
4. 開店時 renderer 的畫布被重設大小 3 次（每次都重新配置繪圖緩衝區）。
5. 每格都重建陰影簽章字串、`new Matrix4()`（低／中畫質根本沒開陰影）。
6. 動態解析度會被單一次卡頓（編譯 shader、生客人、GC）拉低解析度。
7. 標籤貼圖快取上限 400 張（每張都是一張 GPU 貼圖）。

## 改了什麼

| 項目 | 做法 |
|---|---|
| 程式拆分 | `main.ts` 不再靜態匯入 `game.ts` / `net.ts`；改用 `loadGame()` 動態載入（three.js、渲染器、店面模型、本地模擬）。主選單先出現，選單閒置時（`requestIdleCallback`）預先載入，所以通常點下去就能開店；載入失敗會回主選單顯示提示。商城的 3D 試穿預覽（`cosmetics.ts`）也改成用到才載入。原本 `game.ts` / `cosmetics.ts` 裡讓選單設定的狀態（常客、店內劇情、商城裝飾）移到沒有 three.js 的 `shift-ctx.ts`。 |
| PWA 離線 | `sw.js` 安裝時讀 `index.html` 與入口 JS 的匯入表，把所有分出去的 chunk 一起預先快取，第一次造訪沒開過店也能離線玩單人。 |
| 模型釋放 | 新增 `Human.dispose()`：客人／其他玩家離開時釋放身體、奧客配件等自己的 geometry 與標籤材質（共用快取的 geometry 不動）。 |
| 共用模板 | 手上拿的東西（`heldModel`：箱子、咖啡、便當、拖把，也用在地上掉落物與箱子堆）與購物籃，每種只合併一次，之後用 `clone()`（共用 geometry 與材質），撿起／放下不再產生新的 GPU 緩衝區。 |
| 生客人卡頓 | SkinnedMesh 的包圍球改用綁定姿勢的 geometry 包圍球再加 0.6 m（手臂舉起、翻滾也包得住），省掉逐頂點骨架運算。 |
| 畫布大小 | `resize()` 只有寬高或像素比真的變了才重設（開店時原本會重設好幾次，現在只 1 次）。低畫質像素比上限 0.85、中 1.25（原本就有）。 |
| 每格配置 | 陰影簽章只在有開陰影（高畫質）時計算；blob 陰影改用共用 Matrix4。 |
| 動態解析度 | 單一格卡頓（> 250 ms 且 > 目前平均 4 倍）不計入 FPS，避免開店編譯 shader 或生客人時被誤判而降解析度；本來就有的升降門檻（< 75% 降、> 95% 升）不變。 |
| 標籤貼圖 | 快取上限 400 → 240 張（一個忙碌班次實際用到約 100–150 張）。 |
| 背景暫停 | 原本就有：分頁隱藏時 `frame()` 直接 return，不渲染；單人模式也會暫停模擬與音效。 |
| 字型 | 原本就有：`<link rel=preload>` + `font-display: swap`，且已子集化（新增文字要跑 `scripts/font-subset.py`）。 |

刻意沒做的：

- **按地圖拆分 decor／道具**：`decor.ts` 壓縮後只有約 23 KB，而且已經在「進遊戲才載」的 game chunk 裡；再按地圖拆只省十幾 KB，
  卻會在開店時多一次網路往返，不划算。
- **更多 InstancedMesh**：貨架商品本來就是 InstancedMesh（每種商品一個），靜態道具也都合併成每材質一個 mesh，
  每格 draw call 只有 32–58 個；剩下的大多是每位客人一個 SkinnedMesh，改 instancing 需要重寫骨架動畫，風險大、收益小。
- **低畫質把圓角方塊換成直角**：可以省加油站約一半三角形，但會明顯改變「玩具感」外觀，沒做。
- **圖示壓縮**：PNG 量化後明顯有色階，而且圖示不在主選單的關鍵路徑上，沒動。

## 改善後（同樣條件，before / after 交替各跑兩輪）

### 首次載入

| 項目 | 改善前 | 改善後 |
|---|---|---|
| 入口 JS（未壓縮） | index 610 KB + three 568 KB | index 176 KB + sim 130 KB + map 50 KB + 小檔（共約 365 KB），three.js 與遊戲（189 KB）改為按需載入 |
| 主選單前下載的 JS（gzip，實測傳輸量） | **約 350 KB** | **約 135 KB**（-61%） |
| 手機：主選單可操作 | 4.0–4.3 秒 | **2.0–2.2 秒** |
| 手機：點地圖到第一格畫面 | 3.5–3.6 秒 | 2.9–3.0 秒（3D 程式已在選單閒置時預載） |
| Deck：主選單可操作 | 0.2–0.3 秒 | 0.4 秒（本機不限速，差距在負載雜訊內） |

### 記憶體洩漏測試（`tests/e2e/perf.mjs`，低畫質 844×390，快轉約 40 位客人進出）

|---|---|---|
| renderer geometry 數 | 61 → 98（+37） | 59 → 54（不增加） |
| JS heap（GC 後）變化 | **+11.6 MB** | −1.5 MB |

### 營業中（中位數；機器負載極高，畫面時間只供參考）

| 地圖 | 裝置 | draw call | 三角形 | 配置量 KB/秒 | GC 次數 / 10 秒 | 每格 JS p50 / p95 (ms) |
|---|---|---|---|---|---|---|
| 便利商店 | 手機・低 | 45 → 42 | 3.6 萬 → 3.4 萬 | 1420 → 1470 | 5 → 17 | 13 / 46 → 13 / 47 |
| 超市 | 手機・低 | 32 → 51 | 3.0 萬 → 4.2 萬 | 1590 → 1370 | 8 → 12 | 11 / 37 → 14 / 39 |
| 加油站 | 手機・低 | 53 → 49 | 7.8 萬 → 7.7 萬 | 1320 → 1180 | 12 → 13 | 15 / 32 → 13 / 63 |

draw call／三角形的差異來自畫面裡剛好有幾位客人、站哪裡（模擬有隨機性），不是程式造成的；配置量與 GC 次數同樣
在雜訊範圍內。**營業中每格的效能這次沒有可靠的改善證據**：在軟體繪圖下 84% 以上的時間花在模擬 GPU（`(program)`），
JS 本身每格只有十幾毫秒（4× 降速後）。這輪真正確定的改善是「主選單快一倍」與「長時間營業不再洩漏」。

## 還沒做、需要真機的

- 在真的低階 Android（例如 2–3 GB RAM、Mali-G52 等級）與 Steam Deck 上量 FPS、溫度與耗電，確認動態解析度的實際表現。
- 字型 295 KB 是首次載入最大的單一檔案；可以再拆成「選單用字」與「遊戲內用字」兩個子集（`unicode-range`）。
- 三角形最多的是加油站的靜態合併 mesh（約 3 萬），若真機上加油站特別慢，再考慮只在低畫質減少遠處道具的段數。
